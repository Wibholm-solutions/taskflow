# Plan: Split useTasks hook into smaller modules (#56)

**Issue:** #56
**Date:** 2026-04-05
**Base branch:** master (at `2e614d5`)

## Context

`client/src/hooks/useTasks.ts` is 345 lines after the undo-complete feature (#55/#57).
It manages five distinct concerns:

1. **Task state** — active/upcoming lists, loading, error, refresh, auto-error-clearing
2. **Task CRUD** — create, update, delete with optimistic rollback
3. **Completion queue** — 5s undo delay, pendingCompletions array, timer management, MAX_PENDING eviction, beforeunload flush via sendBeacon
4. **Subtask confirmation** — pendingCompletionTask dialog state (409 confirmation flow)
5. **Reorder** — optimistic reorder with rollback

The goal is to extract concerns 3 and 4 into dedicated hooks, keeping each module under ~200 lines.

## Current Architecture

```
App.tsx
  └── useTasks() → { active, upcoming, loading, error, clearError, refresh,
                      completeTask, pendingCompletionTask, confirmPendingCompletion,
                      cancelPendingCompletion, pendingCompletions, undoCompletion,
                      flushCompletions, deleteTask, createTask, updateTask, reorderTasks }
```

### Consumer: App.tsx
- Destructures the full return object
- Passes `pendingCompletions` + `undoCompletion` to `<CompletionSnackbar>`
- Renders subtask confirmation banner using `pendingCompletionTask`, `confirmPendingCompletion`, `cancelPendingCompletion`
- Passes CRUD callbacks to `<TaskList>`, `<TaskModal>`

## Target Architecture

```
App.tsx
  └── useTasks() → same public API (no consumer changes)
        ├── useCompletionQueue(deps)  — manages pendingCompletions, undo, flush, beforeunload
        └── useSubtaskConfirmation(deps) — manages pendingCompletionTask dialog state
```

**Key constraint:** `useTasks` return type must not change. App.tsx and all consumers remain untouched.

## Extracted Hooks

### 1. `useCompletionQueue`

**File:** `client/src/hooks/useCompletionQueue.ts` (~100 lines)

**Responsibilities:**
- `pendingCompletions` state (PendingCompletion[])
- `enqueue(entry)` — add to queue, start timer, evict oldest if >MAX_PENDING
- `undoCompletion(taskId)` — cancel timer, return snapshot for restoration
- `flushCompletions()` — fire all pending API calls, clear queue
- `beforeunload` handler — sendBeacon for pending completions
- Timer cleanup on unmount

**Interface:**
```typescript
interface CompletionQueueDeps {
  onComplete: (taskId: string, options?: CompleteTaskOptions) => Promise<void>;
  onRestore: (snapshot: Task, list: 'active' | 'upcoming', index: number) => void;
  onError: (message: string) => void;
  refresh: () => Promise<void>;
}

interface CompletionQueueResult {
  pendingCompletions: PendingCompletion[];
  enqueue: (entry: Omit<PendingCompletion, 'timerId'>) => void;
  undoCompletion: (taskId: string) => void;
  flushCompletions: () => void;
}
```

**Design notes:**
- `onComplete` wraps `api.completeTask` — queue doesn't import api directly
- `onRestore` callback lets useTasks handle setActive/setUpcoming (queue doesn't own task state)
- `onError` callback for surfacing errors to useTasks' error state
- Timer IDs managed internally; cleanup in useEffect return

### 2. `useSubtaskConfirmation`

**File:** `client/src/hooks/useSubtaskConfirmation.ts` (~40 lines)

**Responsibilities:**
- `pendingCompletionTask` state
- `setPending(task)` — set the task awaiting confirmation
- `confirmPendingCompletion()` — triggers completion with `completeRemainingSubtasks: true`
- `cancelPendingCompletion()` — clears pending state
- Auto-clear when task no longer exists in state

**Interface:**
```typescript
interface SubtaskConfirmationDeps {
  onConfirm: (taskId: string) => void;
  taskExistsInState: (taskId: string) => boolean;
}

interface SubtaskConfirmationResult {
  pendingCompletionTask: Task | null;
  setPending: (task: Task) => void;
  clearPending: (taskId: string) => void;
  confirmPendingCompletion: () => void;
  cancelPendingCompletion: () => void;
}
```

### 3. Refactored `useTasks`

**File:** `client/src/hooks/useTasks.ts` (~170 lines)

**Remains responsible for:**
- Task state (active/upcoming/loading/error)
- refresh, auto-error-clearing
- completeTask orchestration (delegates to queue or subtask confirmation)
- deleteTask, createTask, updateTask, reorderTasks (optimistic rollback)
- Pure helper functions stay as module-level functions

**Wiring:**
```typescript
export function useTasks() {
  // ... task state ...

  const subtaskConfirmation = useSubtaskConfirmation({
    onConfirm: (taskId) => completeTaskRequest(taskId, true),
    taskExistsInState: (id) => taskExistsInState(active, upcoming, id),
  });

  const completionQueue = useCompletionQueue({
    onComplete: (taskId, options) => api.completeTask(taskId, options),
    onRestore: (snapshot, list, index) => {
      if (list === 'active') setActive(c => restoreTaskInList(c, snapshot, index));
      else setUpcoming(c => restoreTaskInList(c, snapshot, index));
    },
    onError: (msg) => setError(msg),
    refresh,
  });

  // ... CRUD operations ...

  return {
    // same shape as before — no consumer changes
  };
}
```

## Helper Functions

The four pure helpers (`findTaskLocation`, `restoreTaskInList`, `taskExistsInState`, `reorderActiveTasks`) stay in `useTasks.ts` since they operate on the task lists owned by that hook. They could move to a `taskHelpers.ts` util file in a future refactor, but that's out of scope.

## Risks

- **Closure stale state:** The completion queue timers close over callbacks. Using `useCallback` with correct deps and callback-based state updates (`setPendingCompletions(prev => ...)`) mitigates this. This is the same pattern already used.
- **Timer cleanup:** Must ensure all timers are cleared on unmount. The existing beforeunload + useEffect cleanup pattern transfers directly.
- **No consumer changes:** The return type of `useTasks()` must remain identical. This is enforced by keeping the same return object shape.
